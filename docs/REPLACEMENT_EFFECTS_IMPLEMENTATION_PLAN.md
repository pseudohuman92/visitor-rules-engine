# Replacement effects: implementation plan

## Goal

Add Magic-style replacement effects to the rules engine as first-class rules
objects. A replacement effect modifies, redirects, or prevents an event before
the event changes game state. This is different from a triggered ability: a
trigger observes an event that already happened and may then cause another
effect.

This document proposes an incremental implementation. It is a design plan, not
a claim that the engine currently implements these rules.

## Current architecture and the main constraint

The current `Event` type is an enum plus an `Arraylist<Object>` payload. It is
used to notify triggered abilities. [`Events.processEvents`](../src/main/java/com/visitor/game/parts/Events.java)
drains queued events and calls registered cards after the calling action has
already performed its mutation. [`EventChecker`](../src/main/java/com/visitor/card/containers/EventChecker.java)
is therefore a poor place to implement replacement behavior: it runs too late
and can run an effect or put an ability on the stack.

Several important actions mutate state directly:

- [`Actions.destroy`](../src/main/java/com/visitor/game/parts/Actions.java)
  queues a death event and then calls `Card.destroy()`.
- [`Card.moveToZone`](../src/main/java/com/visitor/card/Card.java) extracts a
  card and puts it in its destination directly.
- [`Damagable.receiveDamage`](../src/main/java/com/visitor/card/properties/Damagable.java)
  applies shields, changes health, handles trample/lifelink/death, and only then
  queues a damage event.
- `Actions.draw(playerId, count)` calls `Player.draw(count)` directly. A Draw
  event factory exists, but this path does not enqueue it.
- [`Playable.resolve`](../src/main/java/com/visitor/card/properties/Playable.java)
  runs effects and moves the resolving card through its configured destination
  callback.

The central design task is to move the “would happen” decision ahead of these
mutations without breaking the existing event queue, card hooks, or action
ordering. Matches already serialize actions on a per-match worker, and the
decision system can suspend an effect while a player responds; see
[`MATCH_EXECUTION.md`](MATCH_EXECUTION.md). Use that machinery for choices
rather than adding threads or bypassing the worker.

## Rules behavior to support

Before coding, write a short rules contract for the subset this engine will
support. At minimum, define these points:

1. **Which event is being replaced?** Identify the subject, source, affected
   player or object, proposed amount or destination, and cause.
2. **Which replacements are active?** Start with battlefield permanents, plus
   effects that apply to the object entering play. Add other source zones only
   when a card needs them.
3. **Who chooses?** When several applicable effects can change the same event,
   choose according to the affected player/object rules. Do not use registry or
   hash-map iteration order as a substitute for a rules choice. Add simultaneous
   multi-player ordering rules in a later step.
4. **Can a replacement be declined?** Model optional “you may” replacements as a
   choice. Mandatory replacements should not prompt.
5. **How are chains handled?** After a replacement changes the event, discover
   replacements that apply to the new event. Track application per event
   instance so an effect cannot loop on the same event. Events generated by a
   replacement get their own IDs and their own replacement pass.
6. **What is one event?** A replacement for “draw a card” may need to run for
   each card in a draw of several cards. Wording that replaces “one or more
   cards” may instead apply to the batch. Representing both cases explicitly
   avoids making the current `draw(count)` implementation decide the rules by
   accident.

Prevention effects should use this same pre-event pipeline, with a specialized
result such as “reduce the damage amount” or “prevent the damage.” They should
not be treated as post-damage triggers.

## Proposed model

Keep the existing `Event` and `EventChecker` path for after-the-fact triggers.
Add separate typed objects for proposed events and replacement effects.

An initial event model could include:

- `ZoneChangeIntent(card, fromZone, toZone, cause)`
- `DamageIntent(source, recipient, amount, combat, cause)`
- `DrawIntent(player, count, drawUnit)`

Give each proposed event an ID, optional parent ID, and a set of replacement
effect IDs already applied to that event instance. Keep the event’s data typed;
do not reuse the generic `Arraylist<Object>` trigger payload.

Define a `ReplacementEffect` interface with two responsibilities:

- `appliesTo(event, gameState)`: a side-effect-free applicability check.
- `replace(event, context)`: returns a structured result, such as unchanged,
  modified, redirected, prevented, or replaced by a sequence of new intents.

An effect must not mutate zones, health, or cards while being tested for
applicability. Its result should describe the change; the event coordinator
owns the mutation. A card may register several replacement effects, just as it
can register several event checkers, but replacement registration and
unregistration should be explicit and ordered.

Use a coordinator on `Game` or a focused rules service:

```text
propose intent
  -> collect currently applicable replacements
  -> choose one when rules require a choice
  -> apply its rewrite or prevention result
  -> re-evaluate the resulting event
  -> commit the final event(s)
  -> emit existing trigger events for what actually happened
```

The coordinator should return an outcome that callers can inspect. For
example, a destroy attempt redirected to exile should report that the card
left play and its final destination, but that it did not die. A fully prevented
damage event should report zero damage dealt. A replacement that creates
multiple resulting actions should return an ordered event plan, not perform
those actions itself.

### Suggested code boundaries

Keep rule data and state mutation in separate packages so callers cannot
accidentally apply a rewrite themselves:

| Proposed area | Responsibility |
| --- | --- |
| `com.visitor.game.events` | Typed intent classes, event IDs/causes, rewrite outcomes, and the replacement coordinator |
| `com.visitor.card.properties` | A card-facing replacement capability with applicability and rewrite callbacks |
| `Game` or `game.parts` | Registry of active replacement sources and the single commit path for final intents |
| `Messaging` / decision layer | Human choice prompts and pending replacement decisions |
| AI action policy | Choosing among the same legal replacement options exposed to a human |

The exact package names can follow the repository’s existing organization. The
important boundary is that card definitions describe replacements while one
coordinator alone commits them. A replacement source should have an explicit
lifecycle: when it becomes active, when it stops applying, and whether it can
apply to its own object entering play. Do not reuse the trigger registry until
its source-zone and timing semantics are made explicit.

## Example: a creature that would die is exiled instead

Suppose a unit has lethal damage and a battlefield permanent says to exile that
unit instead of putting it into the discard pile.

1. Damage is proposed and processed. If damage is not prevented or changed and
   the unit becomes lethal, the engine proposes a `ZoneChangeIntent` with cause
   `DESTROY` / “would die”; it has not yet queued a death trigger or moved the
   card.
2. The coordinator checks replacement effects that apply to this would-die
   event. The applicable effect rewrites the destination to exile.
3. The coordinator commits one move from play to exile. Play-leave cleanup runs
   exactly once.
4. It emits the actual zone-change notification. It does not emit Death,
   because the card did not enter the discard-pile zone.

This gives both replacement effects and ordinary triggers a precise point in
the lifecycle. A death trigger can only observe a completed move to the discard
pile; a replacement can only alter the still-pending move.

## Recommended implementation phases

### Phase 1: contract and coordinator

Document the supported rules subset and add the typed event/result classes.
Implement a deterministic replacement coordinator with no user prompts yet.
Use small test doubles to cover no replacement, one automatic replacement,
full prevention, a chain of two different replacements, and an attempted loop.

Keep this coordinator separate from `Events.processEvents()`. The trigger queue
should receive notifications only after the coordinator commits the final
result.

### Phase 2: zone changes and “would die”

Make zone change the first integrated event family because `destroy`,
`moveToZone`, and `putTo` are shared mutation paths. Add a single replace-aware
move operation, then route card destruction and normal resolution destinations
through it.

Important invariants:

- Do not call `leavePlay`, deregister sources, clear card state, or detach
  attachments until the final destination is known.
- If a card leaves play for exile instead of the discard pile, run the
  appropriate leave-play cleanup, but do not emit a “died” event. For this
  engine, death should mean that a card actually moved from play to the
  discard-pile zone.
- If a destruction replacement keeps a card in play, do not run leave-play
  cleanup.
- For an “enters play tapped” replacement, set the entering card’s state before
  registering its triggers and emitting `Enter_Play`.
- Replacements that apply to a card as it enters must be checked even though
  the card is not registered as an active battlefield source yet.

Then audit direct calls to `extractCard`, `putTo`, `Card.moveToZone`, and
`Playable.resolvePlaceCard` to make sure none bypass the new coordinator.

### Phase 3: damage and prevention

Create a `DamageIntent` before `Damagable.receiveDamage` changes health. Resolve
replacement and prevention effects first, then pass the final damage amount to
the existing damage calculation. Preserve the engine’s ordering for shields,
temporary health, trample, lifelink, deadly damage, lethal checks, and trigger
notifications; make that order explicit in code and tests.

Only emit the damage trigger with the amount that was actually dealt. Effects
based on damage dealt, including lifelink and damage triggers, must not use the
original proposed amount if a replacement changed or prevented it. Ensure
trample spillover creates a separate damage intent so it gets its own
replacement pass.

### Phase 4: draw and other event families

Route draws through `DrawIntent`. Decide whether the engine needs an individual
intent per card, a batch intent, or both, and encode that distinction rather
than inferring it from count. Check library-empty loss only after replacement
processing determines that a draw actually occurs. Then migrate other card
movement and resource events as they become necessary.

Avoid migrating every mutation in one change. Add a temporary diagnostic guard
or code-review checklist for direct writes that bypass the coordinator, then
remove any transitional escape hatches once all callers are migrated.

### Phase 5: player choices, AI, and client protocol

Add a decision prompt for choosing among applicable replacements and for
accepting or declining optional replacements. Replacement choices happen
before an event commits and do not create stack objects. Register a pending
decision before sending the prompt so an immediate AI response is safe. Keep
the original event context while waiting; no partial zone or health mutation
should be visible.

Use one choice policy for humans and AI. The AI should receive the same legal
replacement choices and event summary, then choose a result. If a new wire
prompt is required, update the shared protocol and client as a separate,
compatible change. During the first server-only phases, automatic mandatory
replacements can be implemented without a new prompt type.

The replacement prompt should identify the event in terms the player can
understand, list only the effects that still apply, and return a stable effect
ID rather than a list index. Validate the selected ID against the pending
decision when the response arrives. Recompute applicability after applying the
choice; a response must not be able to select an effect that was removed or
made inapplicable while the decision was pending. Because the match worker
preserves the event context, this does not require applying any partial state
changes before the prompt.

## Ordering and loop protection

For each proposed event:

1. Find effects that apply to the current version of the event.
2. If only one mandatory effect applies, apply it.
3. If several apply, request the rules-defined chooser’s selection.
4. Mark the chosen replacement as applied to this event instance.
5. Re-check applicability against the rewritten event.
6. Stop when no replacement applies, or finish if the event is prevented.

Include an iteration safeguard that fails loudly with the event and effect IDs
when a replacement chain does not terminate. Do not silently drop effects at a
fixed limit. When an effect produces separate events, queue them in the order
required by the rules and process each with its own event identity. Make
simultaneous-event/APNAP ordering a documented follow-up rather than letting
container order determine it.

## Testing checklist

Add unit tests for the coordinator and integration tests for real game actions:

- No replacement preserves current action results and trigger behavior.
- A “would die, exile instead” replacement leaves the card in exile, performs
  leave-play cleanup once, and emits no death trigger.
- A card that actually moves from play to discard emits one death event after
  the move.
- “Enters tapped” is visible to enter-play effects.
- Damage prevention/reduction runs before health loss and lethal checks; only
  actual damage drives lifelink and damage triggers.
- Trample spillover is a distinct replaceable damage event.
- Draw replacements handle single draws, batched draws, and an empty deck
  without double drawing or incorrectly ending the game.
- Multiple replacement effects use the right chooser, optional effects can be
  declined, and chained effects terminate.
- Replacements work during normal play and while an effect is awaiting a
  decision on the match worker.
- AI and human decisions choose from the same applicable effects.

Add a regression test for every card that uses the new API. Keep existing
trigger-ordering tests: replacement processing must happen before those events
are queued, without changing the established order among after-the-fact
triggers.

## Suggested first vertical slice

The lowest-risk first feature is an automatic “if this would die, exile it
instead” replacement. It exercises event proposal, source registration,
destination rewriting, leave-play cleanup, and the distinction between a
replacement and a death trigger without requiring a new client choice prompt.
Once that path is covered by integration tests, add damage prevention and then
interactive replacement ordering.
